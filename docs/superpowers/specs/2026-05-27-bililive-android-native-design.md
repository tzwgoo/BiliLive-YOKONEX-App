# Bililive 安卓原生独立端设计文档

> 日期：2026-05-27
> 主题：将 `BiliLive-YOKONEX` 重构为原生安卓独立运行 App

## 背景

当前项目 `BiliLive-YOKONEX` 是一个基于 `Python + FastAPI` 的本地直播互动控制台，主要能力包括：

1. 接入 B 站直播事件。
2. 支持礼物、点赞、弹幕关键词触发。
3. 支持将命中事件派发到下游 WebSocket 指令服务。
4. 支持 EMS 蓝牙设备接入与波形触发。
5. 通过本地 Web 控制台统一完成监听、连接、规则配置与事件观察。

用户希望新增一个**原生安卓独立端**，并明确要求：

1. 新程序放在 `D:\BiliLive-YOKONEX-App`。
2. 安卓端必须能**独立运行**，不依赖电脑上的本地服务。
3. 第一版只接入**第三方房间消息流**，不做 `open-live`。
4. App 要支持**后台 / 锁屏后尽量持续监听并触发**。
5. 输出目标需要支持**蓝牙 EMS** 与**下游 WebSocket 指令服务**，并且可切换。
6. 蓝牙首发即支持当前桌面版覆盖的**两种 EMS 设备协议**。
7. 波形不做重新设计，直接迁移当前桌面版的**现有内置波形**。
8. UI 采用**移动优先重做**，不追求复刻桌面控制台布局。

## 目标

本次设计目标如下：

1. 在安卓端提供一个可独立安装、独立运行的直播互动 App。
2. 只接入第三方房间消息流，也能接收礼物、点赞、弹幕事件。
3. 支持后台常驻监听，并通过前台服务提升挂机稳定性。
4. 支持两类输出目标：
   - 本机蓝牙 EMS 设备
   - 下游 WebSocket 指令服务
5. 支持礼物、点赞、弹幕关键词规则配置，并根据当前输出模式执行动作。
6. 保留并迁移现有桌面版的 EMS 内置波形、两种协议识别和封包逻辑。
7. 提供符合安卓习惯的移动端页面流，而不是沿用 Web 控制台思路。

## 非目标

第一版明确不做以下内容：

1. 不接入官方 `open-live`。
2. 不保留本地 HTTP API 和内嵌 Web 控制台。
3. 不实现完整的自定义波形可视化编辑器。
4. 不实现 OBS 小窗。
5. 不支持多设备同时连接或同时输出。
6. 不支持多个下游 WebSocket 服务并发管理。
7. 不支持桌面版与安卓端共用一套运行时。

## 现状与迁移边界

当前桌面版的结构已经比较清晰：

1. `app/main.py`
   - 装配整体服务、状态与路由。
2. `app/api/routes.py`
   - 对前端暴露 HTTP API 和事件流。
3. `app/static/app.js`
   - 负责浏览器控制台交互。
4. `app/bluetooth/service.py`
   - 承载蓝牙配置、波形、规则和运行时封装。
5. `app/bluetooth/runtime/bleak_runtime.py`
   - 负责 EMS 设备识别、`ems_v1` / `ems_v2` 协议分支和波形封包执行。

因此安卓重构应当：

1. 迁移**业务概念与协议知识**：
   - 礼物 / 点赞 / 弹幕事件模型
   - 规则命中逻辑
   - `command_one` 到 `command_ten`
   - 现有内置波形
   - `ems_v1` / `ems_v2` 协议识别与封包思路
2. 不迁移**桌面外壳实现**：
   - FastAPI 路由
   - HTML 模板
   - 浏览器状态刷新逻辑
   - SSE 事件流页面
   - `bleak` 运行时本身

换句话说，安卓端复用的是现有项目的业务规则、协议资产和产品约束，而不是 Python + Web 的技术壳。

## 方案选择

本次确认采用“**过渡型原生**”方案，并在后续演进为纯安卓原生架构：

1. UI、服务、蓝牙、WebSocket、后台运行全部采用原生安卓实现。
2. 业务模型与规则结构尽量映射现有桌面版，降低迁移成本。
3. 首版不为追求抽象完美而过度设计，但从一开始保持清晰分层。

不采用的方案：

1. 直接把当前 Python 程序封装成 APK。
   - 后台、蓝牙、权限与稳定性风险都太高。
2. 安卓 UI + 内嵌 Python 本地服务。
   - 会让进程管理、BLE、后台保活和调试边界更复杂。
3. 用 WebView 简单包现有页面。
   - 不能满足“安卓独立端 + 后台监听 + 原生蓝牙”目标。

## 整体架构

建议在 `D:\BiliLive-YOKONEX-App` 新建独立安卓工程，采用 `Kotlin + Jetpack Compose`，整体结构按以下边界组织：

1. `app`
   - Compose 页面层
   - 导航、权限引导、状态展示、用户操作入口
2. `domain`
   - 核心业务模型
   - 规则判断
   - 输出路由
   - UseCase
3. `data`
   - 第三方房间消息流接入
   - WebSocket 指令服务接入
   - 安卓 BLE 实现
   - 本地存储读写
4. `service`
   - 前台服务
   - 监听生命周期编排
   - 通知栏与后台运行协调
5. `shared`
   - 结果封装、日志、常量、时间格式、序列化工具

### 运行主链路

运行时分成两条主线：

1. 监听链路
   - 连接第三方房间消息流
   - 解析礼物、点赞、弹幕
   - 转为统一事件模型
2. 输出链路
   - 根据规则判断生成动作
   - 按当前模式路由到：
     - 蓝牙 EMS 执行器
     - WebSocket 指令执行器

### 第一版不保留的桌面结构

1. 不保留本地 Web 控制台。
2. 不保留本地 HTTP API。
3. 不保留浏览器轮询 / SSE 状态更新模式。
4. 不保留桌面版的页面层文件组织。

## 页面结构与用户流程

第一版采用移动优先重做，建议做成 `5 个主页面 + 1 个前台服务通知入口`。

### 1. 首页 / 控制台

作用：

1. 显示当前是否在监听。
2. 显示当前房间、输出模式、蓝牙 / WebSocket 状态。
3. 展示最近事件流和启动入口。

核心操作：

1. 启动监听
2. 停止监听
3. 切换输出模式
4. 快速进入蓝牙或规则配置

### 2. 直播连接页

作用：

1. 配置第三方房间消息流。
2. 管理房间号和自动重连开关。
3. 展示后台运行说明。

第一版只保留：

1. 房间长 ID
2. 自动重连开关
3. 后台运行提示

### 3. 输出配置页

分为两个分段：

1. 蓝牙分段
   - 扫描设备
   - 设备列表
   - 连接 / 断开
   - 当前设备信息
   - 固定波形测试
   - 规则绑定波形选择
2. WebSocket 分段
   - `WS URL`
   - `UID`
   - `TOKEN`
   - 登录 / 断开
   - 当前连接状态

### 4. 规则页

分三组配置：

1. 礼物规则
2. 点赞规则
3. 弹幕关键词规则

每条规则的动作统一表示为：

1. 触发蓝牙波形
2. 触发 WebSocket 指令槽位

### 5. 事件日志页

展示：

1. 事件类型
2. 用户信息
3. 事件摘要
4. 是否命中规则
5. 输出是否成功
6. 失败原因

### 首次使用流程

建议流程如下：

1. 首次启动 App。
2. 完成权限引导：
   - 通知权限
   - 蓝牙权限
   - 定位相关蓝牙权限
   - 后台运行说明
3. 配置房间号。
4. 根据需要连接蓝牙或登录 WebSocket。
5. 至少配置一条规则。
6. 回到首页启动监听。
7. 进入前台服务常驻状态。

## 核心数据模型与规则系统

第一版应当彻底区分“事件”和“动作”，避免输入类型与输出通道耦合。

### 1. 统一事件模型

建议定义 `LiveEvent`：

1. `id`
2. `type`
3. `timestamp`
4. `userId`
5. `userName`
6. `roomId`
7. `payload`

`type` 首发支持：

1. `gift`
2. `like`
3. `danmaku`
4. `system`

载荷建议拆分为：

1. `GiftPayload`
   - `giftName`
   - `giftNum`
   - `price`
   - `totalPrice`
2. `LikePayload`
   - `likeCount`
   - `likeText`
3. `DanmakuPayload`
   - `message`

### 2. 规则模型

建议统一为 `TriggerRule`：

1. `id`
2. `enabled`
3. `eventType`
4. `name`
5. `cooldownSeconds`
6. `conditions`
7. `actionBindings`

条件按事件类型区分：

1. 礼物规则
   - `minPrice`
   - `maxPrice`
   - `triggerMode`
2. 点赞规则
   - `likeMultiple`
3. 弹幕规则
   - `keywords`
   - `matchMode`

### 3. 动作模型

建议统一为 `OutputAction`，第一版只支持：

1. `BluetoothWaveformAction`
   - `waveformId`
2. `WebSocketCommandAction`
   - `commandSlot`

### 4. 输出模式

运行时保留全局模式：

1. `bluetooth`
2. `websocket`

规则本身建议按输出目标保存一组 `actionBindings`，例如：

1. `bluetoothAction`
2. `websocketAction`

执行时根据当前输出模式只选择对应通道动作。这样第一版仍然是“单模式执行”，但数据模型已为后续双发保留扩展空间。

### 5. 波形模型

波形模型直接映射现有桌面版：

1. `WaveformDefinition`
   - `id`
   - `name`
   - `builtin`
   - `steps`
   - `executionMode`
   - `loopCount`
2. `WaveformStep`
   - `durationMs`
   - `channelA`
   - `channelB`
   - 保留迁移现有内置波形所需的底层参数

### 6. 本地日志模型

建议单独保存 `EventLogRecord`：

1. `id`
2. `eventType`
3. `summary`
4. `rawPayloadJson`
5. `matchedRuleId`
6. `outputMode`
7. `outputSuccess`
8. `outputMessage`
9. `createdAt`

### 7. 执行流程

规则执行建议按以下顺序：

1. 原始消息进入解析层。
2. 转为统一 `LiveEvent`。
3. 记录原始事件日志。
4. 筛选匹配的启用规则。
5. 判断条件与冷却。
6. 生成待执行动作。
7. 按当前输出模式调用蓝牙或 WebSocket 执行器。
8. 回写执行结果日志。

## 后台服务、连接生命周期与保活策略

既然第一版要求切后台或锁屏后尽量持续工作，运行核心必须放在前台服务中，而不是 UI 页面中。

### 1. 前台服务职责

建议实现 `LiveMonitorService`，统一持有：

1. 第三方房间消息流连接
2. 当前输出模式
3. 蓝牙连接管理器
4. WebSocket 指令连接管理器
5. 规则执行器
6. 日志写入器
7. 重连调度器

### 2. 生命周期状态

建议拆分为三层：

1. `UI 状态`
   - 页面是否打开、当前导航位置
2. `Service 状态`
   - `idle`
   - `starting`
   - `running`
   - `reconnecting`
   - `stopping`
   - `error`
3. `连接状态`
   - 直播消息流状态
   - 蓝牙状态
   - WebSocket 状态

### 3. 启动监听流程

建议按以下顺序：

1. 校验房间号配置。
2. 读取当前输出模式。
3. 若当前模式是蓝牙，则检查蓝牙设备状态。
4. 若当前模式是 WebSocket，则检查 WebSocket 登录状态。
5. 启动第三方消息流连接。
6. 启动前台服务并更新通知栏。

注意：

1. 监听链路与输出链路不应强耦合。
2. 即使蓝牙未连接或 WebSocket 未登录，只要用户明确允许，监听仍可启动，但状态必须清晰提示。

### 4. 重连策略

建议分别管理三条链路：

1. 直播消息流
   - 断开后指数退避重连
2. 蓝牙
   - 仅对最近一次连接设备尝试自动重连
3. WebSocket
   - 断线自动重连
   - 鉴权失败则停止重连并提示用户修复配置

### 5. 后台运行策略

建议采用：

1. `Foreground Service`
2. 常驻通知栏
3. 必要时引导用户关闭电池优化
4. 在文案中明确说明不同品牌手机的后台限制差异

### 6. 异常处理原则

第一版建议遵循：

1. 采集链路异常不直接崩服务。
2. 输出链路异常不反向停止采集。
3. 每条失败都独立记日志。
4. 只有用户显式点击“停止监听”时才整体停机。

## 蓝牙 EMS 与 WebSocket 输出边界

### 1. 蓝牙 EMS 第一版范围

蓝牙首发支持：

1. 扫描附近设备。
2. 识别并连接当前桌面版支持的两种 EMS 设备协议。
3. 断开当前设备。
4. 记住最近一次连接设备。
5. 手动测试内置波形。
6. 规则命中后触发现有内置波形。
7. 展示基础连接状态和失败原因。

蓝牙首发不做：

1. 自定义波形可视化编辑器
2. 多设备同时连接
3. 多设备广播触发
4. OBS 小窗
5. 高级运行图表和复杂诊断页

### 2. 协议支持

第一版蓝牙必须同时支持现有桌面版的两种协议：

1. `ems_v1`
2. `ems_v2`

迁移要求：

1. 协议识别逻辑映射现有桌面版的设备名和服务特征判断思路。
2. 波形封包逻辑迁移现有 `create_waveform_packets` 和 `create_stop_packet` 的行为。
3. 安卓端改用原生 BLE 特征写入，不再依赖 `bleak`。

### 3. 波形迁移要求

第一版直接迁移当前桌面版现有内置波形，不重新设计波形库。

迁移范围包括：

1. 内置波形定义
2. 波形分段结构
3. 执行模式
4. 规则绑定波形的方式

### 4. WebSocket 输出第一版范围

第一版 WebSocket 只保留核心能力：

1. 使用 `ws_url + uid + token` 登录下游服务。
2. 保持连接状态。
3. 规则命中后发送固定 `command_slot`。

首发继续沿用现有固定槽位：

1. `command_one`
2. `command_two`
3. `command_three`
4. `command_four`
5. `command_five`
6. `command_six`
7. `command_seven`
8. `command_eight`
9. `command_nine`
10. `command_ten`

### 5. 输出失败处理

1. 蓝牙失败只影响蓝牙动作，不影响监听继续运行。
2. WebSocket 失败只影响指令发送，不影响监听继续运行。
3. 断线后按各自重连策略处理。

## 测试策略与实施阶段

### 阶段一：运行骨架打通

范围：

1. 安卓工程初始化
2. Compose 主导航
3. 前台服务骨架
4. 房间号配置
5. 第三方房间消息流基础连接
6. 首页状态展示
7. 本地日志落库

成功标准：

1. 可启动前台服务。
2. 可连接第三方房间消息流。
3. 可看到事件进入本地日志。
4. 切后台后服务仍保持运行。

### 阶段二：输出能力接入

范围：

1. WebSocket 登录与发送
2. 蓝牙扫描、连接、断开
3. 两种 EMS 协议识别与写入
4. 现有内置波形迁移
5. 输出模式切换
6. 手动测试波形 / 手动测试指令

成功标准：

1. 可登录下游 WebSocket。
2. 可扫描并连接两种 EMS 设备。
3. 可手动触发内置波形。
4. 事件命中后可成功发 `command_slot` 或蓝牙波形。

### 阶段三：规则与稳定性收口

范围：

1. 礼物规则
2. 点赞规则
3. 弹幕关键词规则
4. 冷却控制
5. 自动重连
6. 通知栏状态完善
7. 权限引导与后台运行说明
8. 错误提示与日志回写

成功标准：

1. 三类事件都能稳定命中规则。
2. 锁屏 / 后台场景下大多数情况下继续工作。
3. 断线可自动重连。
4. 失败有明确状态与日志反馈。

### 测试分层

建议分四层测试：

1. 单元测试
   - 规则命中逻辑
   - 价格区间判断
   - 点赞倍数判断
   - 弹幕关键词匹配
   - 输出模式路由
   - `ems_v1` / `ems_v2` 封包结果
2. 集成测试
   - 第三方消息流解析到统一事件模型
   - 规则执行到动作生成
   - Room / DataStore 读写
   - WebSocket 登录与消息发送
3. 设备联调测试
   - 两种 EMS 设备实机验证
   - 多次连接 / 断开 / 重连
   - 锁屏后波形触发验证
4. 场景回归测试
   - 长时间监听
   - 弱网重连
   - 蓝牙断连恢复
   - 输出模式切换后继续监听

## 风险与对策

### 1. Android BLE 设备兼容性

风险：

1. 两种 EMS 协议首发就要一起支持，联调面会扩大。

对策：

1. 协议适配集中在 `data/bluetooth` 层。
2. 先把封包与执行逻辑做成可单元测试的纯 Kotlin 函数。
3. 尽早安排两种设备的真机联调。

### 2. 后台保活存在机型差异

风险：

1. 不同品牌系统对锁屏和后台服务限制不同。

对策：

1. 使用前台服务与通知栏常驻。
2. 提供忽略电池优化引导。
3. 文案上明确“尽量持续运行”，避免过度承诺。

### 3. 现有桌面功能范围过大

风险：

1. 如果第一版试图完整迁移桌面体验，容易 scope 失控。

对策：

1. 首发只保留第三方消息流。
2. 不做自定义波形编辑器。
3. 不保留桌面版控制台布局与所有附属工具页。

## 验收标准

以下全部满足时，视为第一版安卓原生独立端设计达标：

1. 安卓 App 可独立运行，不依赖电脑端本地服务。
2. 只接第三方房间消息流，也能稳定接收礼物、点赞、弹幕。
3. 可切换输出目标为蓝牙或 WebSocket。
4. 两种 EMS 设备都可完成连接与现有内置波形触发。
5. 可在后台 / 锁屏场景下通过前台服务尽量持续运行。
6. 规则命中后可稳定执行蓝牙波形或 `command_slot`。
7. 失败场景有明确状态提示和本地日志记录。
8. 整体方案已适合进入后续实施计划拆解。
